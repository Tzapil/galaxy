# Как расширять игру: ресурсы, здания, технологии, модули, корпуса

**Руководство.** Сопроводительный документ к `galaxy-sim-spec.md`.
Практика добавления нового контента так, чтобы он встроился в существующие цепочки и
не сломал баланс.

Все данные лежат в `galaxy-sim-data/` и являются **чистым JSON без кода**. Это не
случайность, а решение №7: глубина — это контент, а не код. Движку всё равно, 25 у вас
ресурсов или 250.

---

## 0. Железное правило

**Никогда не добавляйте контент без прогона инструментов.**

Из сорока с лишним дефектов, найденных за время работы над проектом, **ни один не был
виден в статических данных**. Числа, которые «на глаз выглядят разумно», регулярно давали
мёртвый контент, доминирующие стратегии и неразрешимые тупики.

Обязательный цикл:

```
придумал → вписал в JSON → node validate.mjs → node tech.mjs → node design.mjs
                                     ↓
                         node bootstrap.mjs → node galaxy.mjs
                                     ↓
                              прочитал ЧИСЛА, а не только «ошибок нет»
```

Последний шаг — самый важный. Валидатор скажет «ошибок нет» и на данных, где ваш новый
модуль вытеснил половину существующих. Смотреть надо на **состав проектов** и на
**таблицы стоимостей**.

---

## 1. Общие принципы

### 1.1 Новинка обязана занять свободный угол, а не быть лучше

Самая частая ошибка при добавлении контента — сделать вещь, которая **строго лучше**
существующей. Она не расширяет игру, а сужает её: старый вариант просто исчезает из всех
проектов.

Правильный вопрос при проектировании: **что новинка отдаёт взамен?**

| Новинка | Что даёт | Что отдаёт |
|---|---|---|
| Наноброня | вдвое меньшая масса | ниже рейтинг и структурный бонус, нужно редкое сырьё |
| Комплекс РЭБ | не требует орудийных систем, легче | вдвое прожорливее, не наносит урона |
| Канонерка | максимум орудий за деньги | почти нет защиты, один утилитарный слот, малый запас хода |
| Аркология | втрое больше жилья на слот | три слота вместо одного, нужны наноматериалы |
| Предметы роскоши | новый уровень довольства | тянут оптику, конкурируя с орудиями за кристаллы |

Если размен не формулируется одной фразой — новинку не стоит добавлять.

### 1.2 Новинка обязана создать связь, а не отросток

Ресурс, который производится из одного и потребляется в одном месте, — это не глубина,
а лишняя строчка. Хороший новый узел **соединяет ветки, которые до него не пересекались**.

Пример: предметы роскоши тянут `оптику` в гражданскую экономику. До них кристаллы уходили
почти целиком в сверхпроводники (военная ветка) и физическую науку. После — гражданский
спрос начинает конкурировать с орудиями за одно и то же редкое сырьё. Это создаёт
осмысленное решение там, где его не было.

### 1.3 Проверяйте на доминирование, а не на корректность

`validate.mjs` проверит целостность. Доминирование он не увидит — его видно только в
составе проектов из `design.mjs` и в матрице дуэлей.

## 2. Новый ресурс

**Файлы:** `resources.json`, `recipes.json` (+ рецепт), `buildings.json` (+ здание),
`techs.json` (+ технология).

### 2.1 Определить уровень передела

| Уровень | Что это | Откуда берётся |
|---|---|---|
| 1 | сырьё | шахта/буровая/ферма, вход только энергия |
| 2 | первичный передел | один вид сырья + энергия |
| 3 | компонент | два-три ресурса уровня 2 + иногда редкое сырьё |
| 4 | система | компоненты уровня 3, идёт в модули кораблей |
| 5 | финал | сток: корпуса, станции, потребление населением |

### 2.2 Назначить объём

`unitVolume` — **ключевой и самый недооценённый параметр**. Он определяет промышленную
географию: объём должен падать с уровнем передела, иначе возить сырьё будет так же
выгодно, как готовое, и переработка у месторождения потеряет смысл.

Ориентиры: сырьё 0.8–1.2, передел 0.4–0.8, компоненты 0.15–0.35, системы 0.35–0.8,
данные 0.05, корпусные секции 2.0 (намеренно громоздкие, чтобы верфь притягивала
промышленность к себе).

После добавления смотрите блок «ПЕРЕРАБАТЫВАЙ У ИСТОЧНИКА» в `validate.mjs`: плотность
стоимости при переделе должна расти минимум в 1.5 раза.

### 2.3 Подобрать рецепт под целевую стоимость

Стоимость считается автоматически:

```
стоимость единицы = (Σ стоимость_входов + 0.3 × энергия + 0.5 × рабочие × дни) / выход
```

Смотрите медиану своего уровня в блоке «ВЫБРОСЫ СТОИМОСТИ ВНУТРИ УРОВНЯ». Целевая
стоимость новинки — **от медианы до примерно трёх медиан**. Валидатор ругается на
выбросы больше 4× медианы: такой ресурс либо никто не будет производить, либо он
перекосит всё вокруг.

Подгонять проще всего **выходом**: он делит всю сумму. Меняйте `outputs`, а не входы.

### 2.4 Обязательно прописать сток

Если ресурс потребляется **не рецептом**, а стоимостью постройки или модуля — валидатор
объявит его мёртвым узлом. Так было с наноматериалами: они уходят в наноброню и
аркологию, но ни один рецепт их не ест.

Добавьте его в подходящий сток в `recipes.json`: `ship_construction`,
`station_construction`, `building_construction`, `population`, `research`, `ship_movement`.

### 2.5 Если ресурс потребляется населением

Решите, **жизненно важный он или комфортный**.

- Жизненно важный (еда, вода) — его нехватка убивает население. Добавление такого
  ресурса **сломает бутстрап**: молодая колония не сможет его производить.
- Комфортный (медикаменты, потребтовары, роскошь) — нехватка бьёт по довольству и
  напряжению региона, но не убивает.

**Новые потребности населения добавляйте только комфортными.** Пропишите ресурс в
`comfortOnly` и держите ставку низкой (0.005–0.02 на тысячу населения в день).

## 3. Новое здание

**Файлы:** `buildings.json`, `recipes.json` (если производит), `techs.json` (кто открывает).

Обязательные поля: `slots`, `placement` (`on` и, если нужно, `requires`), `buildCost`,
`buildDays`.

### 3.1 Слоты

Один слот — норма. Два-три — только для стратегических объектов (завод сверхпроводников,
корпусная верфь, региональная столица, аркология).

**Осторожно с многослотовыми.** Жадный строительный ИИ **не умеет** выделять под них
место в насыщенной колонии: они всегда проигрывают текущим дефицитам, которые острее
прямо сейчас. Это известное ограничение (находка F3). Пока оно не устранено, здание на
три слота имеет шанс не быть построенным никогда.

### 3.2 Требование к телу

`placement.requires` привязывает здание к особенности: `ore_deposit`, `ice_deposit`,
`gas_giant_orbit`, `silicate_deposit`, `habitable`, `rare_earth_vein`, `crystal_vein`,
`radioactive_vein`.

**Помните про дефицит мест.** Агрокомплекс требует `habitable`, а пригодная планета в
системе обычно одна и быстро забивается — из-за чего пищевая цепочка упиралась в потолок.
Если ваше здание критично для жизнеобеспечения, подумайте об альтернативном рецепте без
привязки к телу (так появился гидропонный комплекс).

### 3.3 Стоимость постройки

Проверьте, что все материалы **производимы к моменту, когда здание открывается**.
Классический тупик: здание требует композитов, композиты требуют технологии, технология
требует данных, данные требуют этого здания.

Валидатор дерева ловит циклы через научные данные, но **не через произвольные материалы**.
Проверяйте вручную: пройдите по стоимости постройки и убедитесь, что каждый материал
доступен на своём уровне технологий.

### 3.4 Энергия

У каждого тела с производством должна быть **собственная** электростанция: энергия не
транспортируется. Если новое здание ставится на тело, где ничего не было, — стартовому
пакету или строительному ИИ придётся ставить туда и генератор.

## 4. Новая технология

**Файл:** `techs.json`.

### 4.1 Стоимость по тиру

| Тир | Ориентир (сумма по всем видам данных) |
|---|---|
| 1 | 800 |
| 2 | 4 800 |
| 3 | 35 700 |
| 4 | 200 000 |
| 5 | 980 000 |

Кривая ×5 за шаг. Отклоняться в пределах ±40% нормально, дальше — ломает темп партии.

### 4.2 Распределение по видам данных

Смотрите блок «ВЕТКИ» в `tech.mjs`: суммарно физика/инженерия/биология должны держаться
в диапазоне 20–50% каждая. Если один вид опускается ниже 15%, валидатор ругается —
соответствующая лаборатория становится никому не нужна, и целая ветка экономики
оказывается декоративной.

Ориентир по смыслу: физика — энергия, щиты, лучевое оружие, сенсоры; инженерия —
корпуса, двигатели, кинетика, производство, логистика; биология — жизнеобеспечение,
население, колонизация, ассимиляция.

### 4.3 Предпосылки

Граф — **DAG, а не дерево**: у узла может и должно быть несколько предпосылок. Хорошая
технология связывает две ветки (нанофабрикация требует композитных материалов из
промышленности и прецизионной оптики из той же ветки, а открывает вход в защиту и
колонизацию).

Валидатор проверяет отсутствие циклов и достижимость от корня.

### 4.4 Правило бутстрапа

**Всё, что входит в рецепты производства научных данных, обязано быть доступно на нулевом
тике.** Если ваша технология открывает здание, которое нужно для производства данных, —
это цикл, и валидатор его поймает.

Технологии стартовых веток должны давать **модификаторы выхода**, а не доступ.

### 4.5 Типы эффектов

```json
{ "type": "unlockModule",   "id": "..." }
{ "type": "unlockHull",     "id": "..." }
{ "type": "unlockBuilding", "id": "..." }
{ "type": "modifier", "target": "recipe:<id>|building:<id>|module:<id>|family:<name>|global",
                      "stat": "...", "value": 1.25 }
{ "type": "ability", "id": "..." }
```

Каждая сущность фазы 1 должна открываться **ровно одной** технологией — не нулём и не
двумя. Валидатор проверяет обе стороны.

### 4.6 Повторяемые

В конце ветки. `repeatable: true`, `baseCost` ≈ 40 000, `costGrowth` 1.20–1.22, эффект на
уровень скромный (+2%). Без них фракция доисследует дерево и застынет — для партии на
десять тысяч лет это смерть.

## 5. Новый модуль

**Файлы:** `modules.json`, `techs.json`.

### 5.1 Пять бюджетов

Модуль тратит: слот, энергию, массу, экипаж, стоимость. Проект валиден, только если

```
usedSlots[тип] ≤ hull.slots[тип]
Σ powerDraw ≤ 0        (реакторы дают отрицательный расход)
Σ crew ≤ hull.crewCapacity
```

Скорость — не характеристика, а следствие: `Σ тяга / Σ масса`.

### 5.2 Кривая тиров

Тир выше = **лучше за слот, но хуже за кредит**: характеристика ×1.6, стоимость ×2.0,
энергия ×1.7, масса ×1.25 за тир. Это правило держит технологическое превосходство
неабсолютным: бедная передовая фракция строит мало отличных кораблей, богатая отсталая —
много посредственных.

### 5.3 Новое семейство против нового тира

**Новый тир** существующего семейства — простое расширение вверх. Соблюдайте кривую.

**Новое семейство** внутри существующего слота — интереснее, но требует размена.
Спрашивайте себя: почему кто-то возьмёт старое семейство после появления нового?

Проверенные оси размена:
- **масса против защиты** (наноброня против обычной);
- **энергия против массы** (щиты против брони);
- **производственная цепочка** (РЭБ не требует орудийных систем, то есть не конкурирует
  с пушками за одну цепочку);
- **полоса дальности** (плазма бьёт только вблизи, зато сильнее всех).

### 5.4 Оружие

Обязательные поля: `bands` (`long`/`medium`/`short`), `vsShield`, `vsArmor`, `damage`.

Множители держите в коридоре **0.6–1.4**. Более широкий разброс перемножается с
поглощением брони и даёт вырожденные исходы: при 0.5 против брони 84 лазер терял 79%
урона и переставал существовать как класс.

После добавления обязательно посмотрите **матрицу дуэлей** (проверка 3 в `design.mjs`).
Здоровая картина — замкнутый цикл, где никто не бьёт всех.

### 5.5 Что проверять после добавления

1. `node design.mjs` — модуль появился хоть в одном проекте? Если нигде — он бесполезен.
2. Не исчезли ли из проектов старые модули того же слота? Если исчезли — доминирование.
3. Матрица дуэлей — не появился ли билд, который бьёт всех.

## 6. Новый корпус

**Файлы:** `hulls.json`, `techs.json`, `doctrines.json`.

Поля: распределение слотов по четырём типам, `baseMass`, `structure`, `crewCapacity`,
`baseFuel`, `buildRecipe`, `buildDays`.

### 6.1 Корпус должен занять свободную точку пространства

Сравните распределение слотов с соседями по тиру. Канонерка (4/1/2/1) встала между
корветом (2/1/2/1) и фрегатом (3/2/2/2): больше орудий, чем у обоих, меньше защиты и
утилиты, чем у фрегата. Это **другая точка**, а не улучшение.

Один утилитарный слот означает один реактор, то есть жёсткий потолок по энергии — сильное
и осмысленное ограничение.

### 6.2 Обязательно вписать в доктрину

Корпус, не указанный ни в одной доктрине из `doctrines.json`, **не будет использован
никогда**. Это самая частая забытая мелочь.

### 6.3 Проверка отдачи на кредит

Смотрите проверку 6 в `design.mjs`. Здоровый новый корпус даёт отдачу на кредит **в
пределах ±15% от соседей**: он не должен быть ни бесполезным, ни очевидно лучшим.

Помните ограничение B9: проектировщик выбирает по абсолютной оценке, поэтому малый корпус
не будет выбран, даже будучи выгоднее. Это дефект инструмента, а не вашего корпуса.

## 7. Новая доктрина

**Файл:** `doctrines.json`.

Доктрина — это функция оценки плюс жёсткие требования:

```json
{
  "id": "...", "name": "...", "role": "warship|civilian|support",
  "hulls": ["..."],
  "preferredBand": "long|medium|short",
  "weights": { "dps": 1.0, "ehp": 1.2, "speed": 0.2, "intercept": 0.3,
               "cargo": 0, "scan": 0, "mining": 0, "colonists": 0, "troops": 0 },
  "require": { "minSpeed": 3.0, "minCargo": 0, "minScan": 0 },
  "withdrawAt": 0.40, "pursueAbove": 1.6
}
```

Жёсткие требования входят в оценку **как штраф**, а не как фильтр: жадный алгоритм
сначала закрывает минимальную скорость, а уже потом оптимизирует.

Скорость оценивается с убывающей отдачей. При линейной оценке доктрина с высоким весом
скорости выпускала корабли **вообще без вооружения**.

`preferredBand` связывает проектирование с боевой моделью: оружие вне желаемой полосы
оценивается с коэффициентом 0.35.

## 8. Новая механика

Если добавляется не контент, а правило (новый тип потребности, новая ветка напряжения,
новый вид блокады) — оно почти наверняка **не будет учтено** в моделях спроса, которые
считают только рецепты.

Три категории, которые уже пришлось добавлять вручную и которые надо помнить:

1. **Капитальное потребление** — расход на строительство.
2. **Флотский спрос** — топливо кораблей и кораблестроительная программа.
3. **Рекурсивная развёртка по графу** — потребность в композитах, которые нужны для
   постройки верфи, которая нужна для корпусов.

Добавляя новый вид потребления, задайте себе вопрос: **увидит ли его строительный ИИ?**
Если потребитель — не рецепт, ответ «нет», и надо дописывать явно.

## 9. Чек-лист перед тем, как считать работу сделанной

```
[ ] node validate.mjs   → выход 0, нет мёртвых узлов, нет выбросов по уровням
[ ] node tech.mjs       → выход 0, нет циклов, нет циклов бутстрапа,
                          баланс данных ≥ 15% на каждый вид
[ ] node design.mjs     → новинка появилась в проектах;
                          старые аналоги НЕ исчезли;
                          матрица дуэлей осталась цикличной;
                          отдача на кредит в пределах ±15% от соседей
[ ] node bootstrap.mjs  → население не обвалилось, наука пошла
[ ] node galaxy.mjs     → разброс цен не вырос, торговля не встала
[ ] прочитаны ЧИСЛА, а не только строчка «ошибок нет»
```

## 10. Типовые ошибки

| Симптом | Причина | Где описано |
|---|---|---|
| Новый модуль вытеснил старые | сделан строго лучше, а не в размен | B7, B8 |
| Новый ресурс — «мёртвый узел» | потребляется стоимостью, а не рецептом; нет в стоке | A5 |
| Новое здание не строится никогда | многослотовое, жадный ИИ не выделяет место | F3 |
