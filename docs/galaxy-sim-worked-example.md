## Шаг 1. Искать не «что добавить», а «где дырка»

Соблазн при расширении — придумать что-нибудь красивое. Это неверный порядок: красивая
вещь без ниши либо мертва, либо вытесняет существующее.

Правильный первый ход — **посмотреть на данные и найти перекос**. Я задал три вопроса.

### Вопрос 1: какое сырьё имеет слишком мало потребителей?

```powershell
node -e "const r=require('./recipes.json');
  const use={};
  for (const x of r.batchRecipes) for (const k of Object.keys(x.inputs)) (use[k]??=[]).push(x.id);
  for (const k of Object.keys(use)) console.log(k, use[k].length, use[k].join(','));"
```

Результат показал перекос: **редкозёмы и кристаллы уходили почти целиком в сверхпроводники
и оптику**, то есть в военную и научную ветки. У промышленной ветки прямого спроса на
редкое сырьё не было вообще.

Это и есть дырка. Редкое сырьё по решению №9 должно быть предметом конкуренции — но
конкурировать за него было некому: гражданская экономика в нём просто не нуждалась.

### Вопрос 2: где обрывается лестница потребления?

Потребление населением было двухступенчатым: еда и вода (жизненно важное), медикаменты
(комфортное). Для развитой колонии поздней эпохи потолок довольства достигался слишком
рано — третьей ступени не существовало.

### Вопрос 3: есть ли в дереве технологии-пустышки?

```powershell
node -e "const t=require('./techs.json').techs;
  for (const x of t) if (!x.effects || !x.effects.length) console.log('ПУСТО:', x.id);
  for (const x of t) for (const e of (x.effects||[]))
    if (e.type==='unlockModule') console.log('mod', e.id, '<-', x.id);"
```

Нашлась технология `ecm` (радиоэлектронная борьба) — **в дереве есть, а модуля под неё
нет**. Исследование, ничего не открывающее. Готовая дырка, которую надо просто закрыть.

**Вывод шага 1.** Три ниши найдены не выдумкой, а осмотром данных:
промышленный сток для редкого сырья, третья ступень потребления, пустая технология.

## Шаг 2. Сформулировать размен до того, как писать JSON

Для каждой новинки я записал одной фразой, **что она отдаёт**. Если фраза не пишется —
новинку в работу не берём.

| Новинка | Даёт | Отдаёт |
|---|---|---|
| Наноматериалы | промышленный сток редкозёмов и кристаллов | дорогая цепочка, конкурирует со сверхпроводниками |
| Роскошь | третья ступень довольства | тянет оптику, конкурируя с орудиями за кристаллы |
| Наноброня | вдвое меньшая масса | ниже структурный бонус, нужны наноматериалы |
| Комплекс РЭБ | перехват без орудийной цепочки | прожорливее, не наносит урона |
| Канонерка | максимум орудий за деньги | почти нет защиты, один реактор, малый запас хода |
| Аркология | втрое больше жилья на слот | три слота, нужны наноматериалы |

Обратите внимание, что размен у наноброни и РЭБ идёт **по разным осям**: у брони —
масса против характеристик, у РЭБ — производственная цепочка. Второе ценнее: модуль,
который не конкурирует с пушками за одно и то же сырьё, меняет структуру экономики,
а не только арифметику проекта.

## Шаг 3. Посчитать стоимость ДО внесения в JSON

Это ключевой шаг, который легко пропустить. Целевую стоимость я определял по медиане
уровня, а рецепт подгонял под неё — а не наоборот.

### Наноматериалы: уровень 3, компонент

Сначала посмотрел, во что мне надо попасть:

```powershell
node validate.mjs | Select-String -Pattern "УРОВЕНЬ 3" -Context 0,12
```

Медиана третьего уровня — около 30 кредитов за единицу. Коридор: от медианы до примерно
трёх медиан, то есть **30–90**. Целился в верхнюю половину: наноматериалы должны быть
дорогими, иначе они не создадут напряжения в конкуренции за редкозёмы.

Прикидка по формуле `(Σ входы + 0.3 × энергия + 0.5 × рабочие × дни) / выход`:

```
композиты  4 × 14.9 = 59.6
редкозёмы  2 × 11.8 = 23.6
кристаллы  2 × 12.4 = 24.8
энергия    22 × 0.3 =  6.6
труд       5 × 4 × 0.5 = 10.0
                        ------
                  итого 124.6  →  при выходе 3 = 41.5 за единицу
```

41.5 попадает в коридор ближе к нижней трети. Оставил.

**Приём:** подгоняйте `outputs`, а не `inputs`. Выход делит всю сумму, поэтому им
стоимость настраивается одним числом, не трогая смысл рецепта.

### Роскошь: уровень 5, потребительский

Здесь ориентир другой — не медиана уровня, а **платёжеспособность населения**. Роскошь
должна быть заметно дороже медикаментов, иначе она не будет ощущаться как роскошь, но не
настолько, чтобы её вообще никто не производил.

Рецепт `2 оптики + 5 полимеров + 2 медикаментов + 14 энергии → 5 роскоши`. Оптика здесь
не для красоты: именно она протягивает кристаллы в гражданскую ветку, то есть закрывает
дырку из шага 1.

## Шаг 4. Подобрать тир технологии

Ориентиры стоимости: тир 1 ≈ 800, тир 2 ≈ 4 800, тир 3 ≈ 35 700, тир 4 ≈ 200 000,
тир 5 ≈ 980 000.

Тир выбирается **не по «крутости», а по месту в цепочке предпосылок**. Нанофабрикация
требует композитных материалов и прецизионной оптики — обе третьего тира по входу,
значит нанофабрикация тоже третий:

```json
{ "id": "nanofabrication", "tier": 3,
  "requires": ["composite_materials", "optics_manufacturing"],
  "cost": { "engineering": 24000, "physics": 12000 } }
```

Сумма 36 000 против ориентира 35 700 — попадание. Распределение 2:1 в пользу инженерии,
потому что это производственная технология.

Технология корпуса канонерки — тир 2, стоимость 4 800 чистой инженерией, предпосылка
`hull_frigate`. Ровно по ориентиру.

Роскошь — тир 2, но с уклоном в биологию (`bio 3000 + engineering 1800`): это
потребительская технология, а биологическая ветка по проверке баланса данных была самой
недогруженной. **Приём:** когда смысл технологии допускает разные виды данных, выбирайте
тот, которого не хватает по балансу.

## Шаг 5. Первый прогон — и первый дефект

```powershell
node validate.mjs
```

```
ДЕФЕКТ: мёртвый узел — nanomaterials производится, но не потребляется ничем
```

**Что произошло.** Наноматериалы потребляются стоимостью модулей (`nano_armor`) и
стоимостью постройки (`arcology`), но **ни один рецепт их не ест**. Валидатор строит
граф по рецептам и справедливо считает узел мёртвым.

Это не ложное срабатывание. Модель спроса, которая разворачивает потребность назад по
графу, тоже строится по рецептам — значит, промышленный ИИ **не увидел бы** спроса на
наноматериалы и никогда не построил бы нанофабрику.

**Исправление.** Прописать ресурс в стоки — `ship_construction` (через модули) и
`building_construction` (через аркологию). То же самое сделал для роскоши: сток
`population`.

**Урок, вынесенный в руководство:** ресурс, который потребляется стоимостью постройки, а
не рецептом, обязан быть явно указан в стоке. Это отдельный класс дефектов — потребитель
существует, но невидим для планировщика.

## Шаг 6. Второй дефект: наноброня вытеснила обычную

```powershell
node design.mjs
```

Ошибок нет, выход 0. Но я смотрел не на код возврата, а на **состав проектов** — и увидел,
что во всех без исключения проектах поздней эпохи стоит наноброня. Обычная броня Мк2 и Мк3
исчезли полностью.

**Диагноз.** Я задал наноброне высокий рейтинг **и** низкую массу. Получилась вещь строго
лучше существующей — ровно та ошибка, от которой предостерегает раздел 1.1 руководства.
Формально всё валидно; фактически я удалил из игры два модуля.

**Исправление.** Разменять по одной оси, а не выигрывать по обеим. Итоговые числа:

| Модуль | Тир | Рейтинг | Структура | Масса |
|---|---|---|---|---|
| armor_t1 | 1 | 8 | 60 | 40 |
| armor_t2 | 2 | 13 | 96 | 50 |
| armor_t3 | 3 | 21 | 154 | 62 |
| **nano_armor_t1** | 3 | **12** | **62** | **26** |
| **nano_armor_t2** | 4 | **19** | **100** | **33** |

Читается так: наноброня Мк1 даёт рейтинг почти как у обычной Мк2 (12 против 13), но
структурный бонус — как у Мк1 (62 против 60), зато **масса вдвое меньше** (26 против 50).
Плюс требует редкого сырья.

Размен стал честным: наноброня — это «купить лёгкость за редкий ресурс и меньшую живучесть».

**Проверка исправления.** Повторный `node design.mjs` дал ровно то, чего я хотел:

- медленные корабли (линкор, крейсер линейного боя) берут **тяжёлую** броню — им масса не
  критична, а структура важна;
- быстрые (рейдер, эскорт) берут **нано** — им критична скорость, то есть тяга на массу.

Оба семейства живут, и выбор между ними диктуется ролью корабля. Именно так и должно
выглядеть здоровое расширение.

## Шаг 7. Третий дефект: РЭБ вытеснил точечную оборону

Та же процедура — смотрю состав проектов, а не код возврата. Точечная оборона исчезла
отовсюду, где раньше стояла.

**Диагноз.** Комплекс РЭБ давал перехват выше, чем точечная оборона того же тира, при
меньшей массе и сопоставимом расходе энергии. Снова вещь строго лучше.

**Исправление.** Поднял расход энергии до 22 при перехвате 52.

| Модуль | Тир | Перехват | Масса | Энергия | Стоимость |
|---|---|---|---|---|---|
| pd_t2 | 2 | 48 | 12 | 14 | оружейные системы + электроника |
| pd_t3 | 3 | 77 | 15 | 24 | оружейные системы + электроника |
| **ecm_suite_t1** | 3 | **52** | **8** | **22** | электроника + оптика + **сверхпроводники** |

Теперь РЭБ — это «перехват для того, у кого свободна энергия, но занята оружейная
цепочка». Разные корабли делают разный выбор, и оба модуля остаются в игре.

Обратите внимание на **стоимость**: у точечной обороны в рецепте оружейные системы, у РЭБ
— сверхпроводники. Это и есть тот самый размен по производственной цепочке из шага 2:
фракция с развитой оружейной промышленностью пойдёт в ПВО, фракция с развитой
электроникой — в РЭБ. Различие возникает из экономики, а не из правила.

**Проверка.** После правки штурмовик берёт точечную оборону, эскорт — РЭБ. Сосуществуют.

## Шаг 8. Побочная находка: дефект в самом инструменте

Проверяя канонерку, я обнаружил, что она **не выбирается никогда**, хотя по числам должна
быть конкурентоспособна. Стал разбираться — и нашёл ошибку не в данных, а в проектировщике.

**Что было.** Функция выбора лучшего проекта сравнивала кандидатов **по абсолютной оценке**.
Больший корпус почти всегда набирает больше очков просто потому, что в него влезает больше
модулей. Малый корпус проигрывал, даже будучи вдвое выгоднее на потраченный кредит.

**Почему это важно.** Дефект был не в моём расширении, а в инструменте, которым я
расширение проверял. Он **скрывал** реальную конкурентоспособность любого малого корпуса —
то есть все прошлые выводы о малых корпусах были в той или иной степени недостоверны.

**Что сделал.** Добавил в `design.mjs` **проверку 6 — отдача на кредит**: оценка проекта,
делённая на его стоимость. Результат:

| Корпус | Очков на 1000 кредитов |
|---|---|
| Фрегат | 337 |
| **Канонерка** | **335** |
| Крейсер | 299 |

Канонерка попала в 1% от фрегата — то есть занимает свою нишу и не доминирует. Ровно то,
что нужно.

Сам дефект выбора по абсолютной оценке зафиксирован как незакрытый: чинить его надо в
`sim-core`, где выбор корпуса должен учитывать бюджет фракции, а не абстрактную «лучшесть».

**Урок:** когда новинка ведёт себя не так, как предсказывают числа, **подозревайте
инструмент**, а не только данные. Каждая такая проверка — заодно проверка проверяльщика.

## Шаг 9. Финальный прогон всей цепочки

```powershell
node validate.mjs   # экономика: циклы, мёртвые узлы, стоимости, плотность
node tech.mjs       # дерево: циклы, бутстрап, баланс данных, покрытие
node design.mjs     # проекты: 6 проверок, включая матрицу дуэлей и отдачу на кредит
node bootstrap.mjs  # одиночная система: население, наука
node galaxy.mjs     # много систем: сходимость цен, торговля
```

Что я смотрел в выводе, помимо кода возврата:

| Инструмент | На что смотреть |
|---|---|
| `validate.mjs` | новый ресурс не в списке выбросов; плотность стоимости растёт при переделе |
| `tech.mjs` | доля каждого вида данных ≥ 15%; новые узлы достижимы от корня |
| `design.mjs` | новинка появилась в проектах; **старые аналоги не исчезли**; матрица дуэлей цикличная |
| `bootstrap.mjs` | население не обвалилось после новой потребности |
| `galaxy.mjs` | разброс цен не вырос (остался в районе 0.0–0.4) |

Третья строка — самая важная и самая пропускаемая. «Новинка используется» проверяют все;
«старое не перестало использоваться» — почти никто.

## Итоговая процедура в семи строчках

```
1. Осмотреть данные и найти перекос. Не выдумывать — искать.
2. Сформулировать размен одной фразой. Не пишется — не добавлять.
3. Посчитать стоимость по медиане уровня ДО внесения в JSON. Подгонять выходом.
4. Тир технологии = уровень предпосылок, не «крутость». Данные — те, которых мало.
5. Прогнать всю цепочку инструментов.
6. Смотреть на СОСТАВ ПРОЕКТОВ и ТАБЛИЦЫ, а не на код возврата.
7. Новинка ведёт себя странно вопреки числам — подозревать инструмент.
```

За одно расширение эта процедура поймала три дефекта в контенте и один в инструменте.
Все четыре прошли бы в игру незамеченными при проверке «валидатор вернул ноль».
